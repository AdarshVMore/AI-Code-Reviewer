The same product, built to not fall over

Same nine capabilities as today — nothing added, nothing dropped. What changes: services stop importing each other's internals, Redis splits into a queue cluster and a cache cluster, the codebase index becomes something you update one node at a time instead of rebuilding, and hosting stops depending on a wake-up ping.

This is the actual fix for the current design's worst inefficiency: today, opening or updating a PR re-downloads and re-embeds the entire repository regardless of how many files changed. The cost of an update becomes proportional to the diff, not the repo.

Redis: two clusters, not one

Today it's one Upstash instance doing queueing and caching at once, unsharded, unreplicated. That's the single riskiest piece of infrastructure in the whole system.

Queue cluster (Redis Streams, consumer groups replacing plain lPush/brPop) needs durability more than raw speed — a lost job means a PR silently never gets reviewed. Shard by stream name across hash slots; each shard gets a primary plus at least one replica, promoted automatically on failure. Consumer groups give you XACK, so a worker that dies mid-job doesn't lose the job — it just gets redelivered to another consumer in the group.

Cache cluster is the opposite trade: speed over durability. Losing a cache entry just means one slower request, not a dropped job — so it can run allkeys-lru eviction under memory pressure without anyone noticing. Sharded by key hash for horizontal scale, replicas mainly for read throughput and failover rather than durability.

The reason to physically separate them: a cache eviction storm during a traffic spike should never be able to starve or delay the queue, and heavy queue write throughput shouldn't blow a cache-latency budget. On managed Redis (Upstash, ElastiCache) this is two separate provisioned instances; self-hosted, it's two separate Redis Cluster deployments.

Hosting and the CDN's actual job

webhook-service has to be always-on, full stop — GitHub's delivery timeout doesn't care that a request would've woken a sleeping instance in 40 seconds. api-service and the worker pools can autoscale: api-service on request rate behind the load balancer, workers on stream lag specifically (queue depth, not CPU — a worker doing a 30-second Claude call looks idle to a CPU-based autoscaler right up until the queue backs up).

The CDN's job here is narrower than "put Cloudflare in front of everything." Cache the truly public, low-personalization reads at the edge with a short TTL; everything authenticated, and the webhook endpoint specifically, bypasses cache entirely and goes straight to origin. The frontend's static assets and edge delivery stay on Vercel — no reason to rebuild what it already does well.

Neo4j moves to a managed cluster (AuraDB, or self-hosted causal clustering once volume justifies the operational cost) with read replicas for the graph queries that don't need to hit the write primary. Repo archives and CI logs move from ephemeral /tmp disk to object storage (S3), so a worker that dies mid-job doesn't take a half-downloaded repo with it — any replica can pick the job back up.

Bottlenecks, ranked

high

Full-repo re-index on every PR

The current design's worst inefficiency by far — cost scales with repo size, not diff size. Fixed by the incremental indexing pipeline above.

high

Fully sequential Claude call chain

Classify type → search query → main review → gif title, each waiting on the last even where nothing downstream needs it. Parallelize the independent legs; gif title is the one call that genuinely can't move earlier, since it needs the finished review.

medium

One vector index per repo

Fine at a handful of installs, doesn't hold past a few thousand — Pinecone bills and rate-limits per index. Namespaces inside shared indexes instead.

medium

Sequential per-file GitHub writes on fix flows

Deployment and issue fixes patch up to five files one request at a time, risking GitHub's secondary rate limits. Parallelize independent file fetches, batch where the API allows it.

medium

Unsharded, unreplicated Redis doing three jobs at once

Queues and cache on one instance, no failover. Addressed by the two-cluster split above.

low

Dashboard aggregates hitting the write primary

Read replica absorbs this — it's read-heavy, tolerant of a few seconds of replication lag, and shouldn't compete with review writes.

low

Free-tier cold starts

The wake-ping between webhook and worker is a legitimate fix for a real constraint today, not a scaling strategy — always-on hosting retires the whole problem once budget allows.
